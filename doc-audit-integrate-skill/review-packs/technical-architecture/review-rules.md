# 技术架构报告审核规则包

本规则包适用于技术架构报告，只定义审核范围、触发条件、严重级别和证据边界；不改变平台的 `Finding` 契约。

## 通用判定与证据要求

- 审核顺序：先完成全文和表格审核，再审核最终可见图件及图文一致性。
- 每项 Finding 必须有可定位的文本、表格或图片证据。图文问题必须同时具有文本和图片证据；纯文本问题不要求图片证据。
- 图片只证明其可见内容。**图中未画出某组件、链路或高可用标识，只能得出“图未提供该项证据”或“图文不一致”，不得推断生产环境不存在该能力。**
- 图片文字无法辨认、组件对应关系不明确，或无法确认图与正文描述的是同一对象时，使用 `不确定`，说明局限性并提出需补充的材料；不得写成直接冲突。
- 引用图片时，证据说明应描述可见文字、实例、连线、图例或区域；不得使用“见附图”“见视觉提取”等泛化表述替代事实。
- `impact` 仅说明对文档评审、实施准备、容量规划或理解的影响；不得断言已发生生产事故、合规处罚或安全事件。

## 必检规则

### R-TERM-001：内部术语与名词解释

- 严重级别：**重大**。
- 触发条件：文档名词解释/术语表为空、缺失，且正文、表格或架构图中存在 **3 个及以上** 未定义的内部名称、缩写、产品别名或不可识别标签。
- 不触发条件：术语已在首次出现处、名词解释、图例或附录给出中文全称与缩写映射；或未定义术语少于 3 个。
- 结论口径：
  - 正文/表格出现未释义术语：`文本不完整`。
  - 图中术语与正文命名不一致，且可定位到同一对象：`图文不一致`。
  - 图中文字不可辨识：`不确定`，不得臆测其真实缩写。
- 必要证据：名词解释为空/缺失的证据；每个代表性未定义术语的出现位置（至少 3 个，可分布在文本和图件）。
- 整改要求：补充中文全称、英文全称/缩写、业务含义；统一图、表、正文中的同一对象名称。

### R-HA-001：部署图与正文的实例数、可用性模式一致性

- 严重级别：**重大**。
- 触发条件：对可对应的同一组件，部署图中的可见实例数、主备/集群/双活标识，与正文或资源表中的实例数、可用性模式不一致；或正文声明高可用模式但部署图未标明足以核对的实例和关系。
- 结论口径：
  - 图中可数实例与资源表数量不同：`图文不一致`。
  - 图中仅有一个逻辑方框，无法判断其代表单实例还是集群：`未提供图示证据` 或 `不确定`，不得判定实际为单机。
  - 文本或图像对象无法可靠对应：`不确定`。
- 必要证据：同一组件的正文/资源表证据与图中实例、标识或图例证据；必须说明对象映射依据。
- 整改要求：在图中画出可核对的实例、主备/集群/双活关系、VIP/负载均衡等标识，并使图、表、文字采用相同名称和数量口径。

### R-HA-002：高可用设计中的单点风险

- 严重级别：**重大**。
- 触发条件：正文、资源表或图件明确表明承担关键业务路径的应用服务、采集/批处理服务、配置中心、缓存、中间件或数据库为单实例，且文档同时要求高可用、7×24 服务或无中断关键处理。
- 数据库判定：单节点数据库触发；**两节点 active-standby/主备本身不触发本规则**。如规则要求数据库集群而文档仅提供主备，必须在任务输入或独立规则中明确“必须集群”的依据，不能自行假定。
- 不触发条件：文档提供至少两实例及明确的主备、集群或双活运行关系，且没有与之冲突的证据。
- 结论口径：基于表或正文明确“1 台/单实例”可使用 `文本不一致` 或 `文本不完整`；仅从图中未画多实例得到的结论只能是 `未提供图示证据` 或 `不确定`。
- 必要证据：关键服务时段/可用性要求，以及该组件实例数和运行模式的直接证据。
- 整改要求：明确每个关键组件的实例数、故障切换方式、数据一致性策略和依赖关系；图表同步更新。

### R-CAP-001：用户数与并发计算依据

- 严重级别：**重大**。
- 触发条件：用户总数、最大同时在线数、平均同时在线数或并发数缺失计算依据；或无法由文档明确给出的公式、分类和取整规则推导。
- 判定方法：逐用户群校验“用户类别 → 公式 → 取整方式 → 计算结果”。只有总数与结果不一致而缺少类别或取整说明时，结论应为“计算依据不完整”，不得直接声称公式错误。
- 取整：结果为小数且文档未说明向上取整、向下取整或四舍五入时，视为依据不完整；不得自行选择一种取整规则判错。
- 必要证据：公式、用户分类、各用户群原始人数与计算结果。不得使用部署图或模块图作为计算正确性的支撑证据。
- 整改要求：表中逐行补充用户类别、公式、取整规则和计算过程；合计值应可由各行复算。

### R-CAP-002：业务量、数据量、存储量及均值/峰值口径

- 严重级别：**重大**。
- 触发条件：业务处理量、数据处理量、数据存储量任一缺失；或任一指标缺少单位、统计周期、均值/峰值定义、采样窗口或增长假设；或均值与峰值数值相同但未说明两者相同的业务原因。
- 判定边界：均值等于峰值并非自动错误；只有缺少口径/原因，或与已给出的高峰时段、并发量、处理窗口等直接矛盾时，才输出 Finding。
- 必要证据：三类指标表、均值与峰值字段、统计周期/单位；如主张矛盾，还须引用对应的高峰时段、并发量或处理窗口。
- 整改要求：为每项指标明确单位、统计周期、均值/峰值定义、采样窗口、增长假设与数据来源；说明例外值并完成与并发量、批处理窗口、资源配置的交叉校验。

## 扩展一致性检查

下列问题可在有直接证据时提出，但不得替代或弱化上述必检规则：

- 数据接口章节声明“无”，但接口表、数据流图或应用关系表列出了接口：`文本不一致` 或 `图文不一致`。
- 安全设计文字声明了网络边界能力，而网络图无法展示相应边界：`未提供图示证据` 或 `图文不一致`。仅网络图未画防火墙、WAF、DMZ 等，不能断言实际网络层不存在这些设施。
- 灾备等级、RTO/RPO、服务时段和备份设计存在直接、可定位的数字或文字冲突：`文本不一致`。如仅依据通用经验判断“无法满足”，且文档没有相互矛盾的指标，应使用 `不确定` 并列出需要补充的恢复演练、链路、异地副本或容量证明。
